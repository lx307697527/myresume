# 博客编辑手册(定时任务每次运行前必读)

> 这份手册是每日博客任务的**唯一规则来源**。改策略只改这里(走 PR),不用重设定时任务。
> 2026-11-27 定稿:每天跑,不达标就跳过;中英两版;试运行期开 PR、人工合并;严禁透露客户与公司内部资料。

## 1. 这个博客为什么存在

网站 https://myaiwebdev.com 有两类读者:**招人的技术负责人 / HR**,和**想做系统的中小企业老板**。
博客的作用是持续给这两类人、以及 AI 搜索引擎(ChatGPT、Perplexity、豆包、Kimi……)提供
"能被引用的一手经验":每篇从 AllyOS 的一个真实问题出发,讲清问题、解法和实测数字。

**AllyOS 是证据,不是主角。** 没人搜"AllyOS 昨天改了什么",但有人搜"Claude Code 子 Agent 怎么防止改坏代码"。

## 2. 每日流程(按顺序做,任何一步不过就停)

1. **定栏目**:按北京时间的星期几取当天栏目(见第 3 节)。
2. **选素材**:先看 ally-os 仓库 `develop` 分支过去 24 小时合并的改动(`git log --since="24 hours ago" origin/develop`);
   没有合适的,再去存量池(事故单、架构决策、规则)挑。用 `python3 scripts/blog.py hash <编号>` 算出素材指纹,
   用 `python3 scripts/blog.py ledger` 确认这个指纹和主关键词都没用过。
3. **定关键词**:一个"问题式"主关键词(中英各一个),写进 front matter 的 `keyword`。
4. **实测数字**:在 ally-os 里用命令现场数(文件数、测试数、耗时……),记下测量日期。不实测的数字不写。
5. **写稿**:`python3 scripts/blog.py new <英文短链> --pillar <栏目>` 生成中英两份骨架,按第 4、5 节写。
6. **建私有敏感词表**:见第 6 节,写到会话的临时目录,**绝不提交**。
7. **生成 + 检查**:
   ```
   python3 scripts/blog.py build
   python3 scripts/blog.py check --strict --denylist <临时敏感词表>
   python3 scripts/test_blog.py
   ```
8. **逐条自查**:对照第 6 节红线逐条核对一遍,结果写进 PR 正文。
9. **看页面**:本地 `python3 -m http.server` 起站,用 Playwright 截图检查中英文章页(桌面 1280、手机 390、深色),
   确认无横向滚动、无报错。
10. **开 PR**:按第 8 节格式,base `main`,ready(不是草稿)。
11. **不达标就不发**:任何一步过不去、或当天没有达标素材,不开 PR,只把原因告诉主人。漏一天远比发错一篇便宜。

## 3. 栏目与一周节奏(北京时间)

| 周几 | pillar | 栏目 | 写给谁 | 素材从哪来 |
|---|---|---|---|---|
| 一 | `pipeline` | AI 研发流水线 | 技术负责人 | 技能、子 Agent、守卫、钩子、发布列车 |
| 二 | `incident` | 事故复盘 | 技术负责人 | 事故单:症状 → 复现 → 根因 → 修法 → 预防 |
| 三 | `architecture` | 架构取舍 | 架构师 | 架构决策:为什么这样做、放弃了什么 |
| 四 | `business` | 老板视角 | 中小企业老板 | 业务流程怎么搬上线、省了什么;**只讲做法,不碰任何业务数据** |
| 五 | `data` | 数据与权限 | 工程师 | 数据库、权限、迁移、审计的通用做法 |
| 六 | `tools` | 工具短文 | 工程师 | Claude Code 技巧、提示词;正文可短(中文 ≥ 600 字) |
| 日 | `weekly` | 本周数字 | 所有人 / AI 引擎 | 本周 AllyOS 工程数字周报(只用工程计数,不用业务数据) |

当天栏目没有好素材,可以换成其他栏目,但同一栏目一周内不超过 2 篇。

## 4. 每篇的固定结构

front matter(中英两份的 date / updated / pillar / source 必须一致):

```
---
title: 问题式标题(中文约 32 字以内;英文 20–75 字符)
description: 搜索结果里显示的摘要(中文约 45–120 字;英文 100–170 字符)
answer: 一句话答案,放在文章最前面(AI 最常直接摘这一段)
date: YYYY-MM-DD
updated: YYYY-MM-DD
pillar: incident
keyword: 主关键词(问题式,别人真的会这样搜 / 这样问 AI)
tags: 至少 3 个,逗号分隔
source: 素材指纹(blog.py hash 生成;只有 weekly 可以不填)
---
```

正文结构:

1. `## 先说背景:……是干什么的`:先讲这东西为什么存在,用大白话,能用比喻就用比喻。
2. 3–5 个**问题式**二级标题,一次只讲一件事。
3. `## 实测数字`:一张表,每行都有"怎么测的 + 日期"。
4. `## 可以照做的清单`:编号步骤,读者能直接抄走。
5. 引用 1–3 个公开权威资料(官方文档),链接必须在 `_blog/allowed-domains.txt` 白名单里。
6. `## 常见问题`(英文 `## FAQ`):至少 2 个 `### 问题`,每个都有回答。
7. 至少 2 个指向本站的链接(`https://myaiwebdev.com/#allyos`、`/services.html`、相关旧文)。

篇幅:中文正文 ≥ 1200 字(tools / weekly ≥ 600);英文 ≥ 600 词(tools / weekly ≥ 300)。单个代码块 ≤ 15 行。

## 5. 写法

- **第一人称、一手经验**:"我实测了……",不写空泛的"业界最佳实践"。
- **结论先行**:answer 和每节第一句就给结论,再展开。
- **数字带出处和日期**:"68 毫秒(2026-11-26 实测,每 10 毫秒轮询)"。
- **少用术语**:非用不可时先用一句大白话解释。
- **英文版不是直译**:面向英文搜索习惯重写标题和关键词(比如 "claude code worktree git hooks"),
  事实、数字、结论和中文版完全一致;美式英语。
- 不夸大、不编造。不确定的写"未实测"或干脆不写。

## 6. 信息安全红线(最高优先级)

**任何一条命中,当天就不发。**

不能写:

1. 客户、潜在客户、供应商、合作方的名字、品牌、产品名、联系方式、所在地;
2. 员工、同事的真名(包括主人自己的真名和工作邮箱;全站只用化名"晨星·路西法 / Morningstar Lucifer");
3. 任何金额:价格、报价、成本、毛利、加价公式与系数、预算、合同条款;
4. 业务数据:订单量、客户数、营收、转化率等任何经营数字(工程计数可以写:提交数、测试数、守卫数、事故单数……);
5. 配方、原料、配比、工艺参数、供应链信息;
6. 安全细节:权限策略原文、鉴权流程细节、密钥、令牌、内部域名、IP、数据库项目 ID;
7. 内部引用:需求 / 事故 / 决策编号(FEAT-、BUG-、ADR-、RULE-)、PR 与 issue 编号、私有仓库链接、内部文件路径、
   真实的库表名和函数名;
8. 业务裁决原文、内部会议与聊天内容、未公开的计划;
9. 产品功效宣称(营养补充剂行业受监管);
10. 内部工具与内部系统的专有名字(网站上已公开的除外:AllyOS、AllyNutra、TeacherCopilot)。

代码与路径一律改写成通用示例(`tools/repair.py`、`orders`、`app.create_order()`),并在文中注明"已做通用化处理"。

**两道闸**:

- **闸一 · 机器扫描**:`blog.py check --strict` 拦下邮箱、电话、金额、白名单外链接、密钥形状、内部编号、内部路径、
  真实库表名,以及私有敏感词表里的每个词。
- **闸二 · 逐条自查**:写完后对照上面 10 条逐条核对,结果写进 PR。

**私有敏感词表**(第 2 步第 6 点):在会话临时目录建一个文件,一行一个词,包括:

- 主人的真名与工作邮箱(定时任务的提示词里给出);
- 环境变量 `BLOG_DENYLIST` 里的全部词条(如有);
- 当天读过的素材里出现的所有客户名、供应商名、人名、品牌名、产品名、内部系统名。

这个文件**绝不提交**,网站仓库是公开的。

## 7. 不做的事

- 不在 ally-os 里改任何东西、开任何任务或 PR;它只是素材库,只读。
- 不直接推送 `main`,不自己合并 PR(试运行期由主人一键合并;转自动后由仓库的 GitHub Action 合并)。
- 不改首页、服务页的其他内容,不改样式和脚本;发现脚本有问题,单独开 PR 说明。
- 不为了过检查去改检查规则。白名单新增域名要在 PR 里说明理由。

## 8. PR 格式

- 分支:会话分配的分支。标题:`docs(blog): <中文标题>`。
- 正文:

```
## 今天这篇
- 中文:<标题> · 英文:<标题>
- 栏目:<栏目> · 主关键词:<中文> / <英文>
- 为什么选它:<一句话:真实素材 + 对外有搜索需求>

## 信息安全自查(逐条)
- [x] 1 客户 / 供应商 / 合作方:无
- [x] 2 真名与联系方式:无
- ……(第 6 节 10 条逐条写)
- [x] blog.py check --strict:PASS(私有词条 N 个)

## 实测数字出处
<每个数字怎么测的、哪天测的>

## 分发版(可直接贴到知乎 / 掘金,带回链)
<300–500 字摘要 + 原文链接>
```
