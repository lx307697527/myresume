FLAGSHIP CASE · ALLYNUTRA · 2026.07 — NOW 00 / 旗舰案例

一个人 + 一组 AI Agent,
撑起一家公司的业务系统。

先说背景:AllyNutra 是一家做定制配方营养补充剂的代工厂。从客户发来第一封询盘,到报价、打样、下单、采购原料、排产、发货、开票、收尾款 —— 这条链路上的每一步,如今都跑在我主导搭建的 AllyOS 上:客户门户、供应商协同、员工运营系统,一个仓库,一个数据库。

但我真正搭的,是那条让 AI 写代码却不会失控的流水线:任何需求都从同一个入口进来,先被「产品经理 Agent」追问清楚,写成规格, 再由实现、测试、评审三个子 Agent 闭环交付;推送前过 109 道机器守卫,每天 11:11 定格、15:00 准时上线。人只做判断,流程和把关交给机器。

THE PIPELINE 每个需求,走同一条流水线

  1. 01需求INTAKE

    任何任务先认领 issue、分配规格编号,再开独立工作区 —— 顺序本身就是规则。

  2. 02拷问GRILL

    「产品经理 Agent」按业务裁决逐条追问;每个定下来的决定都写回仓库,而不是留在聊天里。

  3. 03规格SPEC

    PRD · 设计 · 测试计划三件套,规格编号贯穿提交、PR 与上线记录。

  4. 04实现BUILD

    大任务由编排器派发:implementer 写、test-runner 分层跑、reviewer 环内评审,主 Agent 只看结构化报告。

  5. 05守卫GUARDS

    109 道自测过的守卫在推送前把关:依赖方向、RLS、金额单一来源、文档同步……缺前提就报错,绝不默默放行。

  6. 06集成DEVELOP

    做完自己开 PR、订阅 CI、红了自己修;不许跳过测试、不许空提交踢 CI。

  7. 07上线RELEASE

    每天北京 11:11 冒烟并定格 release,15:00 合并上 main,周末也不停;不通过的那一张自动退出批次。

Ⅰ

渐进披露

模型从不通读整个仓库。根目录一张地图,每个模块一张子地图,只写指针与不变量 —— 细节会过时,指针不会。

Ⅱ

规格即契约

前端从不直接写表:每次写入都是带审计与事件的受治理 RPC,每张客户表都开行级安全。一个事实,只有一个来源。

Ⅲ

系统会自己变好

每周把事故复盘聚类:同一根因出现两次,就提一条规则;规则成熟了,就变成一道机器守卫。
