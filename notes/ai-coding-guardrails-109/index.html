AI 工程化 · 机器守卫

AI 写代码不失控：如何用 109 道机器守卫替代人工逐行 Review

作者 晨星·路西法 · 发布 2026-11-28 · 数据口径 2026-11-13 公开快照

核心结论

控制 AI 写代码，不是把“请小心”写进 Prompt，而是把每次事故变成可执行的不变量：先由规格明确意图，再由机器守卫在数据库、权限、接口和集成边界反复验证，失败就停止流转。109 道检查替代的是重复逐行找错，不是替代技术判断；人转向审查需求、风险、豁免和规则盲区。

为什么不能靠 Prompt 约束 AI 不改错代码？

Prompt 表达的是期望，守卫验证的是结果。模型可以准确复述“不要破坏权限”，却仍可能在一次表结构调整中漏掉某条 RLS 策略；也可能让函数能够运行，却改变调用方依赖的返回结构。问题不一定是模型“不听话”，而是自然语言要求没有变成一个在每次改动后都必须成立、且能自动判定的命题。

AllyOS 的七步流程是需求→追问→规格→实现→守卫→集成→上线。顺序很关键：先在追问阶段暴露歧义，再把共识写进规格；实现不是终点，只是待验证的候选变更；守卫通过后还要进入集成与上线，而不是把单次生成结果直接当成可交付产品。

对技术决策者而言，真正要采购或建设的不是“更会写代码的模型”，而是一条可拒绝不合格变更的流水线。模型、14 个技能与 6 个子 Agent 都可以提高产出并行度，但只有拒绝权属于确定性的工程机制，产能才不会同时放大缺陷扩散面。关于并行工作的上下文组织，可继续阅读《只给地图不给全文》。

986 份事故复盘怎样压缩成 18 条规则？

本文涉及的 AllyOS 规模数字统一采用 2026-11-13 公开快照：118 天、1,200 个需求、1,527 次数据库迁移、1,270 个 pgTAP 测试、109 道机器守卫、23 个业务模块、80 个边缘函数；另有 986 份复盘沉淀为 18 条规则。它们是同一时点的公开工程记录，不应被解释成缺陷下降比例或审查效率提升比例。

从复盘到规则，不是把 986 篇文档塞回上下文，而是做信息压缩。可操作的转换链是：事故现象→失效边界→可复用原则→机器可判定条件→失败处置。例如，一次“某角色看到不该看的数据”不能直接压缩成“以后注意权限”，而应继续追问：访问是否必须经过受治理 RPC？对应表是否启用 RLS？不同角色的允许与拒绝路径是否都有测试？直到答案能够被自动执行为止。

18 条规则解决跨事故复用，109 道守卫解决不同对象上的具体判定。一条数据访问原则可以落到多张表、多组角色和多个入口；一条接口稳定原则也可以落到多个 Deno Edge Functions。因此，规则数与检查数不是一一对应，更不能把两者相除得出“每条规则平均防住多少事故”。

复盘入库时还要保留证据链：原始失败是什么、哪个边界漏检、新增检查读什么输入、失败时阻断哪一步。这样后续维护者才能区分“这条守卫仍有必要”和“这段脚本只是历史上一直存在”。

109 道机器守卫究竟在哪些边界拦截？

公开事实给出了守卫总量与技术栈，没有给出各分类的数量分布。下表因此是审阅拦截记录的分类框架，不是对 109 道守卫的官方分组或实测覆盖声明。它的用途是让决策者能问清：每类变更由谁判定、证据是什么、失败后停在哪里。

拦截面要证明的不变量可采用的检查方式失败后的动作
规格与变更范围实现对象、约束和验收条件来自已确认规格核对变更是否回应规格；检查禁止触碰的边界退回追问或规格，不让实现自行补需求
数据库与迁移结构变化不破坏既定数据语义围绕 Supabase/Postgres 迁移运行 pgTAP 断言阻止迁移继续流转，保留失败断言
访问控制允许的路径可用，不允许的路径明确拒绝检查 RLS 与受治理 RPC 的角色、输入和拒绝分支按高风险变更处理，不用“页面能打开”替代权限验证
接口与边缘函数调用约定和错误语义没有被静默改变核对 Deno Edge Functions 的输入、输出及调用方契约回到实现或同步修改明确版本化的契约
集成与关键路径局部正确的改动组合后仍符合业务流程用 Playwright 验证关键路径，并衔接集成门禁隔离失败变更，不把多个问题混成一次上线

一道合格守卫至少包含四部分：触发时机、只读或受控输入、确定判定、可见失败原因。如果脚本只在开发者记得时运行，它不是流程守卫；如果只输出“有异常”却不能指出哪个不变量失败，排查仍会退回人工翻日志；如果检查失败后仍能默认继续，它也只是提示。

拦截还应尽量靠近错误产生的边界，但最终门禁不能只信局部结果。数据库测试通过，不代表函数调用方已经适配；函数自测通过，也不代表浏览器里的关键路径完整。这就是七步流程把“守卫”和“集成”拆成两步的原因。

为什么守卫全绿仍不等于无条件上线？

自动检查只能证明“已编码的命题在这次输入下成立”。它不能自动发现尚未被识别的风险，也不能替业务负责人判断一个合规但不受欢迎的变化。规格写错时，实现与测试甚至可能一起把错误执行得非常稳定。因此，全绿是进入下一决策点的资格，不是系统正确性的数学证明。

高频 AI 产出还会制造另一个问题：即使每份变更都有检查结果，只要合入顺序、发布时间和变更边界不清，线上异常仍难定位。解决这一半问题，需要把守卫结果绑定到确定的发布单元。AllyOS 的每日发布列车正是为此设置固定定格与发车窗口，详见《每天 11:11 定格、15:00 发车》。

豁免也必须被治理。合理做法不是给守卫加一个永久跳过开关，而是记录哪条检查、哪次变更、由谁基于什么理由放行，以及何时重新验证。这里描述的是落地时应采用的治理设计，并非公开快照之外新增的效果数据。

人工 Review 应该转向哪里？

机器接管重复判定后，人的工作不是消失，而是转向四类更难形式化的问题。第一，需求是否值得做，追问是否排除了错误假设；第二，规格中的业务语义是否完整，尤其是异常路径与不允许发生的事情；第三，现有守卫是否覆盖了本次变更的新边界；第四，失败或豁免是否符合组织的风险承受度。

代码仍然要读，但阅读目的从“逐行寻找所有问题”变为“理解设计、检查机器难以表达的语义、识别新不变量”。当同一类问题第二次由人眼发现时，管理者应追问的不是谁不够认真，而是为什么它还没有成为机器检查。这样，事故复盘才会改变系统，而不是只改变下一次 Prompt 的措辞。

对准备引入 Claude Code 工程化的团队，可以先选一条最关键的数据或权限不变量做穿透：从规格、实现、测试、拦截记录一路走到上线记录。能完整走通一条，比先复制一百条不了解语义的检查更有治理价值。

可以照做的清单

  1. 把流程固定为需求、追问、规格、实现、守卫、集成、上线，明确每一步的进入条件与拒绝权。
  2. 建立复盘到守卫的转换记录：事故、失效边界、规则、可执行断言、失败动作必须能互相追溯。
  3. 优先形式化数据与权限不变量；围绕 Postgres 迁移、RLS 和受治理 RPC 同时验证允许与拒绝路径。
  4. 为接口与边缘函数核对调用契约，再用 Playwright 验证组合后的关键路径，避免以局部绿代替集成绿。
  5. 让失败输出指向具体不变量，禁止默认静默放行；豁免必须有范围、理由和后续处理记录。
  6. 把守卫结果绑定到可定位的发布单元，并定期复盘未覆盖问题，而不是追求检查数量本身。

常见问题

有了 109 道守卫，还需要人工代码审查吗？

需要，但审查对象应上移。机器负责重复验证不变量，人负责需求是否理解正确、规则是否覆盖真实风险、失败是否值得豁免，以及新事故是否要沉淀成下一条守卫。逐行看语法不再是人的主要工作。

109 道检查是否意味着任何团队都该照抄这个数量？

不意味着。109 是 AllyOS 在 2026-11-13 公开快照中的工程规模，不是通用目标。团队应从自己的事故与关键不变量出发，先让高风险规则可执行，再逐步增加检查；数量本身不代表治理质量。

守卫全绿能否证明系统没有缺陷？

不能。全绿只说明这次改动通过了当前已经编码的检查。未覆盖的需求误解、规则盲区和上游环境变化仍需通过复盘、集成验证与发布审计处理，因此守卫必须与七步流程和发布机制配合。
