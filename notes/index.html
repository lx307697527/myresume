工程笔记 · 四篇系统拆解

AI 工程化笔记：从代码生成到可控交付

作者 晨星·路西法 · 发布 2026-11-28 · 面向中文技术决策者

核心结论

这组笔记讨论的不是如何再提高一次生成的惊艳程度，而是如何建立长期可控的工程系统：用机器守卫拒绝不合格变更，用分层代码地图组织多 Agent 阅读，用发布列车固定审计边界，再在本地桌面知识库中明确数据、检索与加密责任。

这些笔记分别解决哪些工程失控？

每篇都可以独立阅读，也都包含核心结论、真实对比表、可执行清单与常见问题。下表提供文章摘要和直接入口。

工程拆解简短摘要
AI 写代码不失控：如何用 109 道机器守卫替代人工逐行 Review控制 AI 写代码，不是把“请小心”写进 Prompt，而是把每次事故变成可执行的不变量：先由规格明确意图，再由机器守卫在数据库、权限、接口和集成边界反复验证，失败就停止流转。109 道检查替代的是重复逐行找错，不是替代技术判断；人转向审查需求、风险、豁免和规则盲区。
只给地图不给全文：大型仓库下多 Agent 协作的上下文架构大型仓库里，多 Agent 不应各自吞下整库全文，而应先读根地图确定模块与边界，再沿指针读取模块子地图和必要源码。地图负责导航，代码负责事实，守卫负责验证。该架构能清楚界定阅读与维护职责，但目前只有工程机制和公开项目结果，没有做受控基准，不能据此宣称准确率、幻觉率或 token 消耗的确定收益。
每天 11:11 定格、15:00 发车：高频 AI 产出的发布列车机制AI 让改动连续产生，发布却必须有离散边界。AllyOS 每天北京时间 11:11 定格 release、15:00 上 main，本质是用固定车次回答“这批上线到底包含什么、凭哪些检查放行”。时间表不是质量证明；它只有与规格、机器守卫、集成结果和变更清单绑定，才能把高频产出恢复为可审计、可定位、可延迟的工程单元。
零云端外传：如何用 Electron + BM25/向量混合检索在 2 秒内跑通本地教研知识库TeacherCopilot 的本地 RAG 不是把云端接口换个界面，而是把资料解析、检索与数据保护放回桌面边界：Electron + React 18 + TypeScript 承载应用，PaddleOCR 处理图像文字，BM25 与向量检索互补召回，AES-256 用于本地加密。公开口径是本地检索 2 秒内，不包含 OCR、建索引或生成耗时的承诺；具体库、密钥管理和召回率不作臆测。

为什么这四篇要放在一起读？

生成能力进入真实组织后，问题会沿交付链连续出现。上下文过多，Agent 难以保持模块边界；产出过快，人工逐行审查无法成为唯一门禁；合入连续发生，异常时难以重建变化范围；资料一旦离开设备，检索质量再高也无法回答数据治理要求。共同原则是：让边界可见，让判断可执行，让证据能回到源头。

公开案例分别来自 AllyOS 与 TeacherCopilot。AllyOS 的规模数字统一采用 2026-11-13 公开快照；代码地图文章明确没有受控基准，TeacherCopilot 文章也不补写未公开依赖库、密钥管理、召回率或额外性能条件。
