本地 RAG · 离线桌面应用

零云端外传：如何用 Electron + BM25/向量混合检索在 2 秒内跑通本地教研知识库

作者 晨星·路西法 · 发布 2026-11-28 · 只拆解已公开架构事实

核心结论

TeacherCopilot 的本地 RAG 不是把云端接口换个界面，而是把资料解析、检索与数据保护放回桌面边界：Electron + React 18 + TypeScript 承载应用，PaddleOCR 处理图像文字，BM25 与向量检索互补召回，AES-256 用于本地加密。公开口径是本地检索 2 秒内，不包含 OCR、建索引或生成耗时的承诺；具体库、密钥管理和召回率不作臆测。

为什么教研知识库首先要回答“数据去哪儿”？

教研资料的工程难点不只是“能不能搜到”，还包括原始文档、识别文本、索引和检索结果分别保存在哪里，哪些操作需要网络，哪些内容可能离开设备。如果这条数据路径没有先划清，再漂亮的检索界面也无法回答技术决策者最关心的外传边界。

TeacherCopilot 是已上线盈利的离线 AI 桌面应用，公开技术栈为 Electron、React 18 与 TypeScript，覆盖 9 个学科和 6 大教学模块。其本地 RAG 检索、PaddleOCR、BM25 与向量混合检索、AES-256 本地加密，应放在同一条本地知识库链路里理解，而不是把每个名词孤立成营销标签。

一个可用于设计评审的链路是：本地资料进入→必要时 OCR 文本化→形成可检索内容→词法与向量两路查询→融合候选→返回本地资料依据。这是依据公开组件作出的职责拆解，不是对未公开源码目录、依赖包或内部接口的复原。任何联网能力、第三方同步或外部模型调用，都应在具体部署中另行审查，不能仅凭“桌面应用”四字忽略。

Electron 与 React 18 怎样划分桌面应用边界？

Electron 提供桌面应用载体，React 18 与 TypeScript 承担界面和类型化开发。对技术决策者而言，关键不是重复“跨平台桌面”这类泛化优点，而是把交互状态与知识库数据路径区分：界面负责导入、查询和结果呈现，本地检索机制负责从设备内资料中找到候选，任何外部传输都不应被隐埋在按钮之后。

设计评审可以沿三个动作追踪数据。导入时，原文件与 OCR 文本保存在何处；查询时，关键词和向量计算是否都在本地完成；展示时，结果能否回到原始资料位置。公开事实没有给出 TeacherCopilot 的具体进程通信方式、存储库或向量库，因此本文不指定这些实现，也不把某种常见 Electron 写法冒充产品现状。

桌面架构还需要把长任务与交互解耦。OCR、索引构建和检索是不同阶段，产品应分别呈现进行中、成功与失败状态，避免用户把“文档已经选入”误认为“已经可检索”。这是一项落地建议，不是对 TeacherCopilot 未公开界面行为的描述。

BM25 与向量检索为什么需要互补？

BM25 从词项匹配出发，向量检索从语义表示出发。教研查询中，用户可能记得一个确切术语，也可能只描述想要的教学情境。前者需要词法证据，后者需要语义候选；混合检索的架构意义，就是不让一种匹配假设垄断所有查询。

公开事实没有提供 TeacherCopilot 的具体融合算法、权重或候选数量，所以不应补写成某种公式已经上线。决策评审真正需要观察的是：两路结果是否都能追溯，融合后能否返回原文，低质量 OCR 或空结果是否会被清楚呈现。

“本地检索 2 秒内”是已公开性能口径，但它不是召回质量指标。返回得快与找得准必须分别验收：前者记录阶段和条件，后者需要带标准答案的查询集。没有这些实验设计，就不应出现精确的召回率或准确率增幅。

PaddleOCR 在本地知识库链路中负责什么？

PaddleOCR 的职责是把图像中的文字转成后续检索可处理的文本，让扫描资料或图片内容进入知识库链路。它不是 BM25 或向量检索的替代品：OCR 解决“有没有可处理文本”，索引与检索解决“如何按查询找到相关内容”。

OCR 结果应保留与原始资料的关联。这样，检索命中一段识别文本后，用户仍可回到原图或原文核对，避免把识别错误继续当成教学事实。对公式、版式或复杂页面的具体识别能力，公开信息没有给出测试，不应承诺某类内容一定能够准确转换。

数据生命周期也要区分。原始资料导入、OCR 完成、索引更新是不同状态；资料被替换或移除后，对应文本与索引如何更新，是任何本地知识库都需要明确的产品逻辑。这里只提出验收问题，不推断 TeacherCopilot 的内部任务队列、文件格式或去重方案。

AES-256 与 2 秒内分别证明了什么？

AES-256 说明公开架构采用了这一算法进行本地加密，但算法名称不等于完整安全结论。密钥如何生成、保存、恢复、轮换，加密覆盖哪些数据，以及使用中的明文边界，都需要另行审查。现有公开事实没有提供这些细节，本文因此不会杜撰密钥管理方案，也不会把“本地”写成绝对无风险。

“2 秒内”则明确了本地检索的公开响应口径。它没有给出硬件、语料大小、并发、查询类型或计时起止点，因此不应补充成某设备上的普遍保证，更不能扩展到 OCR、建索引和答案生成。技术选型时，可要求在自己的设备与资料上分别记录各阶段表现，但这属于后续验收建议，不是新增产品测试结论。

两项事实共同体现了工程边界：数据保护与检索响应都需要显式设计，但二者互不证明。加密不自动带来检索速度，响应快也不自动证明加密覆盖完整。把指标口径说窄，反而更利于采购、验收和后续维护。

如果团队还要把本地知识库接入多 Agent 工作流，可以借鉴根地图与源码指针的思想：检索结果提供资料入口，原文仍是最终核对依据。若进入正式研发流水线，则应像机器守卫一样，把数据边界和拒绝条件变成可检查规则，而不是只写在产品说明中。

可以照做的清单

  1. 画出原文件、OCR 文本、索引、查询与结果的数据路径，逐项标明是否离开设备。
  2. 分别评审桌面交互、OCR、索引、检索与展示职责，不用一个“本地 AI”标签掩盖外部依赖。
  3. 让 BM25 与向量候选都能追溯到原文，明确融合、去重与空结果的呈现方式。
  4. 保留 OCR 文本到原始资料的关联，对复杂版式单独验收，不默认识别结果等于事实。
  5. 安全尽调单独询问 AES-256 的加密范围与密钥生命周期，不从算法名推断未公开实现。
  6. 把本地检索、OCR、索引构建和答案生成分开计时，记录硬件、语料与查询条件。
  7. 建立带标准答案的教研查询集，再比较词法、向量与混合结果，不预先填写召回率收益。

常见问题

“本地检索 2 秒内”是否包含 OCR 和答案生成？

不能这样扩展。公开口径只覆盖本地检索，不足以证明文档导入、PaddleOCR 识别、索引构建或答案生成也都在 2 秒内完成。评估产品时应分别测量这些阶段，并记录硬件、语料规模与查询条件。

使用 AES-256 是否就不需要审查密钥管理？

不是。AES-256 只说明已公开的加密算法选择，不能回答密钥如何生成、保存、恢复、轮换或随数据迁移。TeacherCopilot 的这些细节未在现有公开事实中提供，技术尽调必须单独核实，不能从算法名称反推完整安全设计。

混合检索能否直接推导出召回率提升？

不能。BM25 与向量检索的互补是机制判断，不等于在特定教研语料上的召回率已经有确定增幅。需要建立带标准答案的本地查询集，对词法、向量和融合结果分别评估，才能给出可复现结论。
